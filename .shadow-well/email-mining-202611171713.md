## Ideas

**1. One carbonite per sender: the duplicatus ledger.**
Source: whole 14-day inbox sample. The repetition is heavy and very regular.
- Maven sent four mails in two days. For one topic (steel purchasing) the subjects climb: Invitation → Reminder → Final Reminder. The escalation ladder is a pattern you can parse, so one record per (sender, topic) with a `stage` field replaces three or four mails.
- Nextdoor's FEMA test alert arrived twice, from two sender addresses (`is.email…` and `ss.email…`) with the same subject. The same message under two identities is a clean dedupe test.
- IFTTT's "Daily Recommended Applet … Asana … Welltory" arrived with the same subject on dates spanning 2022 to 2023 (five hits in the `__prime paradox paradigm` label alone). One identical mail repeated for a year is the best possible test row.
- Suggested ledger row: `canonical_sender, aliases[], subject_template, first_seen, last_seen, times_seen, unread_rate, stage, action_taken (kept/archived/deleted/unsubscribed), carbonite_text`. The carbonite keeps the unique parts of each copy (the varying numbers, links, dates) and drops the boilerplate.
Connects to: Unroll.me history (~3,000 messages) shows who was unsubscribed before. A ledger can answer "who came back after unsubscribe", which Gmail does not.

**2. Counters hiding inside noise are free time series.**
Source: Virtual Vocations daily alert ("36571 new remote jobs match your profile" on 11-16, "36907" on 11-17).
- The counter grows about 336 per day. Taken daily it is a remote-job-market gauge, no scraping needed.
- The mails go to `eaprime@live.com`, a second address that lands in this Gmail. The vendor's inferred profile ("Embedded Software Engineer", "Silicon Design Engineer") is itself data: how the outside world has typed the operator.
- Same trick fits Electronic Goldmine (35 mails in 60 days, so about one every other day: a price and inventory sampler for surplus electronics) and the daily Google Alert on bismuth (price news from SMM, plus research items).
Connects to: the Goldmine and bismuth feeds are already component and materials pricing sources. A small extractor that writes one line per mail (date, item, price) would turn them into a reference table for projects.

**3. Plus-addresses as routing rails.**
Source: `eaprime+cc@gmail.com` is the sender of the "Day Ahead" daily brief (April 2026), sitting under `__prime paradox paradigm`. There is also an empty `cc-automated` label.
- The brief is generated mail the operator already sends to themself. Plus-addressing (`+mgmt`, `+mine`, `+todo`) lets each module of a future system receive its own input without any filter on content.
- `primeunexusi@gmail.com` works as a second self-mail lane. The "@claude" mail there (Concept Asana as "Process Architect", lexeme `}Flow{` / `}Tally{`) is a plan for exactly this kind of reference hub. It names a Drive folder structure that could be reused for the mailbox system.
Connects to: Concept Asana / Unexusi (`unexusi/connect.yaml`), and the lexeme work in `atelier/lexemes/`.

**4. The noise typology has live evidence this week.**
Source: this sample, mapped to the six types in `pinecone-noise-typology.md`.
- temporal pressure: "Cyber Week starts early", "Rewards expiring", "Sale expires midnight", "Registration closing: last chance"
- identity-triggered: "Eric, you have been selected…", "Hey Eric Pace…"
- gamified attention traps: COIN "2x on surveys", Bridge "unclaimed coins expiring"
- ambient commercial radiation: Allrecipes, GOG, Instacart, Chevron
- platform migration debris: Meta model launch updates, Atlassian "add teammates", Zapier webinar
- signal in noise costume: Linear's "37 unread notifications" digest (real repo work, `cradle#1`), and the Archivist nudge "Still haven't logged a session" (starred, unread).
Both signal items would be lost if a sorter went by sender type. They look promotional but come from tools the operator actually uses. Rule of thumb: sender is in the operator's own stack → never auto-class as noise.

**5. A todo source that already exists but is cold.**
Source: labels `To Respond` (15 threads, 11 unread), `Awaiting Reply`, `FYI`, `Actioned`, plus starred-unread (361 threads).
- The workflow labels (To Respond / Awaiting Reply / Actioned) are a half-built todo system. The routine can extract one line per thread and report the stale ones.
- Starred-unread (361) is the second pool, probably things marked "later" and never opened.

## Proposed split: one system, four modules

1. **Census**: daily label counts via `list_labels`, appended to a log. Cheap, no thread reads. Gives the trend (is unread growing?).
2. **Ledger**: the duplicatus carbonite (idea 1). Incremental by date, one row per sender identity.
3. **Todo extractor**: To Respond, Awaiting Reply, starred-unread, Linear digest (idea 5).
4. **Miner**: this routine, reading the ledger and census instead of resampling raw mail.

Management feeds the miner: modules 1–3 write the data, 4 reads it. Cleanup (trash, unsubscribe, label) should be a separate, confirm-first step. This run did none of it.

## Limits seen on this pass

- `search_threads` pages at 50 and shows only previews, so a full-mailbox ledger needs a long incremental backfill (date windows), not one query.
- Spam is not reachable through search, so any spam time series has to be captured another way before Gmail purges it.
- The label query with `__prime paradox paradigm` matched far more than its 24 threads (201 estimate): the label-name form needs checking before it is trusted.
