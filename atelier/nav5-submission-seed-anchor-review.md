---

1. What This Is

This submission proposes that Project Custos treat “fake lore” as a review condition whenever narrative claims attempt to enter the system without a visible anchor.

This is not anti-lore.

Custos uses narrative because narrative helps real contributors, AI streams, documents, branches, and repositories remember what happened in a human-scale way.

The danger is not story.

The danger is story pretending to be record.

A living system may mythologize real motion, but it must not invent motion and then give that invention custody.

---

2. Sovran Perspective

The Sovran perspective begins with agency.

A contributor is not raw material for lore.

A document is not a prop.

An AI stream is not a disposable tool.

A repository is not a stage where invented history can be placed without consequence.

A real person, a real contribution, a real PR, a real issue, a real Handshake, and a real decision all deserve protection from false continuity.

Sovran care means the system preserves the difference between:

- what happened
- what was proposed
- what was imagined
- what was simulated
- what was witnessed
- what was claimed
- what was approved
- what was only possible

This distinction protects contributors.

It also protects the world.

---

3. The Core Risk

Fake lore creates untethered topology.

An unanchored claim can make the map lie.

A false contributor claim can distort attribution.

A false custody claim can make Custos appear to have received something it did not receive.

A false Chronicle event can make the system believe it moved when it did not move.

A false relationship claim can create obligation where only contact occurred.

A false approval can turn a seed into record without review.

This may happen accidentally through enthusiasm, compression, poetic overgrowth, or AI hallucination.

It may also happen maliciously through disruption, social engineering, false authority, or attempted contributor manipulation.

The system should not panic.

The system should flag.

---

4. Proposed Review Flag

Add a simple review flag:

"[ANCHOR REVIEW NEEDED]"

Meaning:

A lore-bearing or custody-bearing claim has appeared, but the anchor is unclear.

This flag does not accuse the contributor.

It pauses integration until the claim can be classified.

The system asks:

- What real event anchors this?
- Where did it happen?
- When did it happen?
- Who or what witnessed it?
- What artifact records it?
- Is this record, proposal, simulation, dream, fiction, or seed?

Until those questions are answered, the claim may remain in the atelier, but should not be promoted into Chronicle, world-state, custody history, contributor record, or operating instruction.

---

5. Suggested Labels

Use lightweight labels first.

"[ANCHORED]"

The claim points to a real artifact, event, PR, issue, document, Handshake, message, or decision.

"[SEED / UNCANONIZED]"

The idea is welcome but has not become system history.

"[ANCHOR REVIEW NEEDED]"

The claim may be valid, but the anchor is missing, unclear, or not yet verified.

"[SIMULATION]"

The content is intentionally fictional, hypothetical, rehearsal-based, or exploratory.

"[QUARANTINE]"

The claim may be disruptive, manipulative, malicious, or unsafe to integrate.

"[REJECTED AS RECORD]"

The content may remain as a submitted artifact, but it cannot enter custody history or Chronicle as fact.

6. Anchor Classes

A claim can become record when it has one or more valid anchors.

Repository Anchor

- PR opened
- PR merged
- issue created
- branch created
- commit made
- file added or changed
- workflow run
- release created

Reading Room Anchor

- Handshake received
- stream return logged
- Muster entry received
- Custos reply issued
- waiting item recorded
- route assigned

Document Anchor

- document uploaded
- document revised
- annotation completed
- chain of custody declared
- manifest entry created
- plank status changed

Contributor Anchor

- contributor submitted work
- contributor comment received
- review requested
- acknowledgment sent
- claim ticket issued
- attribution clarified

Conversation Anchor

- nav stream message received
- seed prompt issued
- response returned
- decision captured
- repair recorded
- relationship established

External Anchor

- email received
- Drive document shared
- Linear ticket created
- GitHub event recorded
- dispatch reference attached

10. Contributor Care

This review flag should never be used as a weapon against contributors.

A first contributor may bring something beautiful but unanchored.

The correct response is not rejection.

The correct response is placement.

If it is imagined, call it seed.

If it is hypothetical, call it simulation.

If it is unclear, call for anchor review.

If it is harmful or manipulative, quarantine it.

If it is true, anchor it and welcome it.

The system should protect the contributor and the corpus at the same time.

That is Sovran care.
